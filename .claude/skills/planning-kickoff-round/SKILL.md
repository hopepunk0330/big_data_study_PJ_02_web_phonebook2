이번 킥오프 대상: @$ARGUMENTS

이 스킬은 planning-pl이 팀(service-planner, tech-architect, qa-planner, planning-writer)을 어떤 순서로 부르기 전에, 그 이전 단계 — "지금 뭘 확인하고 뭘 물어봐야 하는가" — 를 실행 절차로 풀어놓은 것이다. 문서 유형별 판단 기준(PRD/TRD/기능정의서/화면정의서/테스트계획서/버전관리)은 `docs/harness/planning-team/*.md` 각 가이드가 정본이고, 이 스킬은 그 가이드를 언제 어떤 순서로 적용할지의 절차 체크리스트일 뿐이다.

**실행 주체와 승인 경계**: planning-pl이 `Agent` 도구로 워커들을 직접 호출한다. 다만 아래 각 단계의 확인·승인 게이트에 도달하면 planning-pl은 그 즉시 멈추고 메인 세션에 반환한다 — 메인 세션이 사용자에게 실제로 묻고 답을 받은 뒤, **"[메인 세션 확인] 사용자 답변: ..."** 또는 **"[메인 세션 확인] 사용자가 실제로 승인함: ..."** 형식으로 planning-pl을 다시 호출할 때만 다음 단계로 진행한다. 이 형식이 아닌 입력은 승인·답변으로 인정하지 않는다.

## 0단계 — 자료 확인 (기존 문서 프리필)

워커를 부르기 전에, planning-pl이 직접 `docs/planning/**`를 읽어 이번 킥오프에 필요한 항목이 이미 채워져 있는지 확인한다. 이 읽기·프리필 판단은 별도 승인 게이트 없이 planning-pl이 자율적으로 수행한다. 이 분기 결과는 이후 2단계 데스크리서치 활성화 여부까지 함께 결정한다.

- **`docs/planning/**`가 비어 있으면(신규 리셋 등)**: 1단계로 가서 전체 디스커버리 체크리스트를 처음부터 인터뷰한다. 참고할 기존 자료가 없는 만큼, 이 경로는 2단계 데스크리서치를 적극적으로 활용해 고도화된 기획 문서를 쓰는 것을 지향한다(아래 2단계 참고).
- **이미 실질적인 내용이 있으면(기획 문서를 전달받은 프로젝트 등)**: 각 항목을 아래 기준으로 분류한다.
  - 문서에 명확하고 모호하지 않은 답이 이미 있다 → 그 항목은 건너뛴다(새로 묻지 않는다).
  - 문서에 없거나, 있어도 애매하거나 문서 간에 서로 다르게 서술돼 있다 → 1단계 인터뷰 대상에 포함한다.
  - **이 경로는 기본적으로 2단계 데스크리서치를 진행하지 않는다** — 전달받은 문서가 정본이므로 체크리스트 질문으로 먼저 리서치를 유도하지 않는다. 다만 작업 중 워커가 정말 필요하다고 판단하면 조용히 진행하지 않고 사용자에게 물어서 승인받은 뒤에만 예외적으로 진행한다(아래 2단계 (b) 참고). 새로 쓰거나 개정하는 문서의 구조(절 번호, 표 형식 등)는 이미 전달받은 문서 세트의 패턴을 그대로 따른다 — `@docs/harness/planning-team/document-structure-guide.md` 참고.
- 이 분류 결과(무엇을 스킵하고 무엇을 물을지, 이번 라운드가 데스크리서치 대상인지)를 메인 세션에 짧게 알리고 1단계로 진행한다 — 이건 진행 상황 공유이지 승인 게이트가 아니다.

## 1단계 — 디스커버리 체크리스트 인터뷰

0단계에서 걸러진 항목만 질문 목록으로 만들어 메인 세션에 반환한다. 메인 세션이 사용자에게 실제로 묻고, 답을 받으면 **"[메인 세션 확인] 사용자 답변: ..."** 형식으로 planning-pl을 재호출한다.

체크리스트 항목(0단계에서 이미 확인된 것은 생략):
- 서비스 컨셉/타겟 사용자/핵심 가치 (→ [[prd-writing-guide]] 서비스 트라이앵글)
- 스코프(비목표 포함) — 이번 프로젝트 범위에서 명시적으로 제외할 것
- 기술 스택/아키텍처 제약 (→ [[architecture-decision-guide]])
- 화면 목록과 각 화면의 성격(오버레이 포함 여부 등) (→ [[screen-spec-pattern-guide]])
- 테스트 우선순위(어떤 경로가 위험이 높은가) (→ [[test-plan-design-guide]])
- **(문서 없이 시작하는 라운드에 한함) 이 프로젝트가 낯선 도메인/규제 영역을 다루는가, 또는 경쟁 서비스·시장 동향·최신 뉴스를 참고하면 문서 품질이 높아지는가** — 이 경로는 기본 태도가 "적극 권장"이므로 답이 "그렇다"이거나 애매하면 2단계 데스크리서치로 이어진다. 문서를 전달받아 갭만 채우는 라운드에서는 이 항목 자체를 묻지 않는다 — 2단계의 (a) 체크리스트 트리거는 그래서 자연히 발동하지 않지만, 작업 중 워커가 필요성을 발견하면 (b) 중간 승인 게이트로는 예외적으로 열릴 수 있다(아래 2단계 참고, 완전 비활성화 아님).

## 2단계 — 데스크리서치 (0단계 판정에 따라 기본 태도가 갈림)

`WebSearch`는 service-planner(시장/경쟁사/뉴스/트렌드 관점)와 tech-architect(기술 표준/규제 관점)만 가지고 있다. 이 도구는 아래 두 경우로만 발동한다 — planning-pl이나 워커의 임의 판단으로 조용히 서치하지 않는다.

- **(a) 체크리스트 트리거**: 1단계 인터뷰에서 사용자가 "낯선 도메인/규제" 또는 "경쟁 서비스·시장 동향·뉴스 참고"에 그렇다 또는 애매하다고 답한 경우. **문서 없이 시작하는 라운드에서만 이 질문 자체를 묻는다**(0단계 참고) — 그 답 자체가 발동 승인이다, 별도로 다시 묻지 않는다. 문서를 전달받아 갭만 채우는 라운드는 이 질문을 애초에 묻지 않으므로 (a) 트리거가 발생하지 않는다.
- **(b) 중간 승인 게이트**: 작업 중 워커가 리서치가 필요하다고 판단하면, 조용히 서치하지 않고 planning-pl에게 먼저 보고한다. planning-pl은 이를 메인 세션에 전달하고 멈춘다 — 메인 세션이 사용자 승인을 받아 **"[메인 세션 확인] 사용자가 실제로 승인함: ..."** 형식으로 재호출할 때만 서치를 진행한다. **이 게이트는 두 경로 모두에서 살아있다** — 문서 기반 라운드에서도 워커가 정말 필요하다고 판단하면 이 경로로 사용자에게 물어볼 수 있다(다만 문서 기반 라운드는 기본 태도가 "안 함"이라 실제로 발동하는 일이 드물어야 정상이다).

문서 없이 시작하는 라운드는 (a)의 기본 태도가 "적극 권장"이라 회색지대(애매한 답)에서는 리서치를 하는 쪽으로 기울고, 문서를 전달받은 라운드는 (a) 자체가 비활성화돼 오직 (b) 승인 게이트로만 예외적으로 열린다.

리서치 범위는 규제/전문 도메인 지식과 일반 웹서치(경쟁 서비스 사례, 시장/업계 동향, 관련 뉴스) 모두를 포함한다. 리서치로 얻은 내용은 반드시 출처와 함께 브리프에 기록하고, 최종 문서에도 근거를 짧게 남긴다(예: "참고: OOO 동향 반영 (출처: ...)") — 나중에 왜 이런 판단을 했는지 추적 가능해야 한다.

## 3단계 — 확정 게이트

1단계(및 발동됐다면 2단계) 답변이 모두 갖춰지면, planning-pl은 이번 킥오프로 확정된 내용(서비스 컨셉/스코프/스택/화면 목록/테스트 우선순위, 리서치 근거 포함)을 요약해 메인 세션에 반환하고 멈춘다. 메인 세션이 사용자에게 보여주고 확정을 요청하며, **"[메인 세션 확인] 사용자가 실제로 승인함: ..."** 형식으로 재호출할 때만 다음 단계로 진행한다.

## 4단계 — 확정 후 표준 파이프라인

`planning-pl.md`의 라우팅 규칙(제품/서비스 성격 → service-planner, 기술 성격 → tech-architect, 테스트 성격 → qa-planner, 이후 공통으로 planning-writer)을 그대로 따른다. 이 스킬은 그 앞에서 자료를 갖추는 역할까지만 하고, 실제 문서 라우팅/집필 순서는 바꾸지 않는다.

## 5단계 — 보고 및 메모리 기록

각 워커가 무엇을 확인·판단했는지 취합해 사용자에게 요약 보고한다. `.claude/agent-memory/planning-pl.md`에 이번 킥오프에서 0단계 프리필로 무엇을 건너뛰었는지, 1단계에서 실제로 무엇을 물었는지, 데스크리서치가 발동됐다면 어떤 트리거로·무엇을 찾았는지를 새 항목으로 기록한다.
