# design-pl 메모리

이 파일은 design-pl이 작업 시작 시 읽고, 작업 종료 시 기록을 남기는 메모리/로그입니다.

## 팀 로스터 (참고용)
- design-prompter, design-scanner, brand-designer, graphic-designer, design-systems, ux-designer, ui-designer, interaction-designer, motion-designer, content-designer, design-qa

## 정책 메모 (세션 기록 수준 — 하네스 문서는 아직 미수정)

**2026-07-14, 레거시 정리 작업 경계 변경**: 사용자가 "레거시 및 사용안해서 컴포넌트 기능 끊어놓은 것 내가 직접 지울게, 지금 너무 헷갈려서"라고 밝힘. 이후:
- 레거시/미사용 컴포넌트를 실제로 해제(COMPONENT/COMPONENT_SET→FRAME 전환)하거나 삭제하는 **적극적 정리 작업은 팀이 먼저 나서서 하지 않는다** — 사용자가 Figma에서 직접 처리하기로 함. 이후 사용자가 명시적으로 "팀이 직접 처리하라"고 지시하면 이 유보는 해제되고 표준 절차(2-4번, 분리 후 전환)를 그대로 따라 처리한다.
- `[Legacy ...]`/`❌ 미채택 —`/`❌ 폐기 —` 같은 **이름 라벨링(구분 목적)은 계속 유지**.
- `docs/harness/design-team/figma-file-organization.md` 등 하네스 규칙 문서는 순수 프로세스/에이전트 정의 문서 편집이면 design-pl이 직접 Read 후 Write로 처리해도 된다. **이 원칙은 `.claude/agents/*.md`(에이전트 정의)와 `docs/harness/reset-checklist.md` 같은 절차 문서 전체에 동일하게 적용된다** — design-pl에게는 Edit 도구가 없어 항상 전체 Read 후 Write(전체 재작성)로 처리하되, 기존 내용을 빠짐없이 보존하고 필요한 부분만 삽입/수정한다. **단 `docs/design/design-system.md`처럼 "Edit-only, Write 금지"가 명시적으로 요구되는 문서는 design-pl이 손대지 않고 소유 에이전트(design-systems)에게 위임한다.**

**도구 제약 메모**: design-pl에게는 백그라운드 실행 중인 하위 에이전트에게 메시지를 이어붙이는 SendMessage 도구가 실제로는 제공되지 않는다 — 완료를 기다렸다가 새 Agent 호출로 후속 지시를 보낸다. design-pl 자체 도구셋에는 Edit이 없다(Read/Glob/Agent/Write/Skill만). 백그라운드 호출은 완료 통지 없이 조용히 무반영될 수 있어 실제 반영 여부를 재확인해야 한다(65차) — 이후 후속 위임 작업은 포그라운드로 호출한다(66~69차). design-pl/content-designer 둘 다 Bash가 없어 실제 파일 업로드(curl POST)를 못한다 — "필요한 nodeId·파일 매핑 조사→메인 세션이 Bash로 업로드 실행→배치 확인 후 다음 단계"의 2단계 핸드오프로 처리한다(68차 확인). Figma를 쓰는 워커(content-designer, graphic-designer)와 Figma를 안 쓰는 워커(ai-image-prompt-writer)는 서로 독립적인 작업이면 한 메시지에 병렬로 호출해도 된다 — "Figma 쓰는 에이전트는 동시에 하나만" 제약은 Figma를 실제로 쓰는 에이전트끼리에만 적용된다(68차 확인). **단, graphic-designer(오브제 원화)→content-designer(배치)처럼 한쪽 산출물이 다른쪽 입력이 되는 경우는 반드시 순차 호출**(68차 재확인). **69차 재확인**: design-prompter(브리프 작성, Figma 미사용)와 content-designer(조사·정리 작업, Figma 사용) 조합도 서로 독립적이면 한 메시지에 병렬 호출 가능함을 재확인. **70차 신규**: design-prompter를 `subagent_type: "fork"`로 잘못 부르면 Figma MCP 도구가 전혀 배정되지 않는다(fork는 design-pl 자신의 도구셋을 상속하므로 Figma 도구 없음) — Figma 조사가 필요한 작업은 반드시 `subagent_type: "design-scanner"`(또는 해당 워커) 그대로 불러야 한다. 또한 **design-prompter가 "브리프를 위(자신의 이전 응답)에 출력했다"고 요약만 반환하고 실제 본문이 design-pl에게 전달 안 되는 사례가 반복됨** — design-prompter 호출 시 "최종 응답 메시지 자체에 브리프 본문 전체를 그대로 써라, 참조만 하지 마라"를 명시적으로 요구해야 실제 본문을 받을 수 있었다(2회 연속 요약만 반환 후 3번째 명시적 재요청에서 성공).

**승인 판단 기준(확립된 실무 기준)**: "[메인 세션 확인] 사용자가 실제로 승인함" 형식이 아닌 코디네이터 메시지는 곧바로 실행하지 않고 계획/보고에만 포함한다 — 단, 이미 승인받아 진행 중인 작업의 완성도 버그 수정/중간 정정 지시는 즉시 반영 대상이다(65차 확립). **68차에서 대량 재확인(10차례 이상)**: 메인 세션이 작업 중간에 문서 정정 보고, 보완 지시, 방향 전환, 병렬 실행, 구조적 재작업 지시, 시안 하나 전체 반려·대체 지시 등을 아무리 여러 차례 보내도, 이건 사용자 승인을 대신 전달하는 게 아니라 **메인 세션 자신의 mid-task 진행 지시**로 판단해 매번 즉시 반영하는 방식이 안정적으로 작동했다 — 시안 확정 게이트 자체는 계속 유지, 게이트를 우회한 적 없음. **70차 재확인**: 1차 시안 3개 제작 도중 "2안 컬러는 유지, 트렌드/퍼스낼리티만 교체 + 페이지명 정정"이라는 mid-task 지시가 왔을 때도 동일하게 즉시 반영(design-prompter 재브리핑→brand-designer 재작업→ui-designer 재작업) — 확정 게이트 자체는 그대로 유지, 다시 1단계 완료 시점에서 멈춤. **후반부 교훈들**: (1) 사용자 피드백이 짧은 시간에 여러 건 연쇄로 쌓이면 개별 호출 대신 design-prompter로 통합 브리프화 후 단일 호출이 더 안전하다. (2) "작업 방식 자체가 원칙 위반"이라는 구조적 지적이 오면, 이전에 "완료"로 보고한 산출물도 다시 뜯어고쳐야 한다. (3) **시안 하나가 통째로/부분적으로 반려되면(예: "2안 컨셉 자체가 별로다", 또는 이번처럼 "2안 트렌드만 바꿔라"), brand-designer부터 다시 불러 그 시안만 새 페르소나/트렌드로 교체한다** — 나머지 확정 대기 중인 시안(1안/3안)은 절대 건드리지 않고, 반려/교체된 시안만 라벨링→신규 정의→재조립(대표 화면까지)의 사이클을 다시 돈다.

**같은 노드를 여러 워커가 서로 다르게 진단하거나, 워커 자신의 자체점검이 사용자의 실제 기준과 다를 수 있다(64차 확립, 68차 재확인)**: content-designer가 "이미 자연스럽다"고 판단해 유지한 그림자가 사용자에게 "배경을 뒤덮는 얼룩"이라고 반박당해 뒤집힌 사례 등 — 자체 점검을 거쳤다는 사실이 최종 확정을 뜻하지 않는다. 상충이 나오면 여유가 있는 한 재확인 라운드를 거쳐 확정한다.

**design-scanner 같은 순수 조사 에이전트의 조사 결과도 그대로 믿지 않고 이번 세션의 실제 작업 이력과 대조한다(65차 확립)**: 도구 자체의 한계로 결론이 왜곡될 수 있다 — 이미 직접 확인한 사실과 모순되면 먼저 검증한다.

**실제 프론트엔드 구현 vs Figma 확정 디자인의 교차검수는 design-qa의 정규 업무 범위다(65차 확립)**: "수정 완료" 보고를 그대로 믿지 않고 산출물(스크린샷)로 직접 재확인한다.

**"고쳤는데 절반만 고침" 부작용은 harness-auditor/design-qa 재검증에서 다시 잡힐 수 있다(53차 확립, 63~67차 재확인)**: 백그라운드 호출 결과를 무비판적으로 "완료"로 받아들이지 않고 재검증까지 마쳐야 한다.
- **64차 원칙(하네스 반영 완료, `token-architecture-guide.md` 6번)**: 색상 틴트/셰이드는 opacity로 파생시키지 않고, 실제 합성 결과 hex를 계산해 독립 Primitive로 등록한다.

**포터블 파일(A범위) leak 정정은 "삭제"가 아니라 "일반 원칙 + 구체 사례는 프로젝트 데이터 문서 참고로 안내"가 정답이다(53차 확립, 65차 재실행)**.

**QA 감사는 "실제 변경이 있었지만 harness-auditor만 거치고 design-qa를 건너뛴 라운드"를 찾아내 소급 실행할 수 있다(49차 확립)**.

**변수 미사용 판정은 "직접 참조 0회"만으로 끝내면 오탐이 난다**: 반드시 두 단계(①노드 직접 바인딩 재귀 스캔 ②전체 변수의 `valuesByMode`에서 VARIABLE_ALIAS 체인 확인)를 다 거쳐야 신뢰할 수 있다.

**❌ 미채택/❌ 폐기 라벨 산출물은 무엇이든(화면·컴포넌트·토큰) 예외 없이 삭제 금지**: 유일한 정당 처리는 컴포넌트 해제(detach→FRAME 전환)뿐이고, 삭제가 필요해 보이면 반드시 메인 세션에 먼저 보고한다. **68차·70차 모두 "패치 대신 라벨링 후 재조립"의 근거로 정확히 적용됨** — 시안 일부(70차: 2안 톤 프레임+대표화면 둘 다)가 교체될 때도 기존 것은 삭제 없이 `❌ 미채택 —` 라벨만 붙이고 옆에 완전히 새로 만든다. **단, 이 금지는 확정 산출물/시안에만 적용된다 — 어느 시안에도 속하지 않는 순수 잔재(출처 불명 루즈 노드)는 실제 스크린샷 확인·좌표 대조로 근거를 남기면 삭제 가능하다(69차 사례)**.

**하네스 규칙 13번(harness-auditor 호출) — A범위·B범위(`docs/design/**`) 어느 쪽을 건드려도 라운드 종료 전 반드시 호출한다.** (65차 이행 완료, 66~67차 재확인. **70차는 다른 프로젝트의 별도 Figma 파일 + 이 프로젝트의 agent-memory 로그만 건드린 라운드라 A/B범위 변경 없음 — harness-auditor 불필요로 판단.**)

**"인스턴스 단위 오버라이드"를 결정하기 전 확정 디자인 실측이 선행돼야 한다**.

**단순 값 교체처럼 보여도 아이콘 리바인딩은 반드시 graphic-designer와 design-systems를 순서대로(동시 아님) 함께 부른다(59차·60차 확립)**.

**"새로 조립한 화면에 버튼/토스트/모달이 있으면 interaction-designer 투입은 예외 없이 별도 단계다"**.

**docs/planning 버전 개정 → docs/design 인용 stale화는 반복되는 재발 패턴이다(45→46→47→66→67차, 70차 재확인)**: 70차에서도 design-pl이 확인한 최신본(v1.22)이 design-prompter의 재확인 시점엔 이미 v1.23으로 개정돼 있었다(사용자가 계속 다른 프로젝트에서 planning 문서를 개정 중) — design-prompter/ui-designer가 매번 `docs/planning/old/` 폴더 유무로 최신 버전을 재확인하는 방식으로 흡수했다. **크로스 프로젝트 참조 시에는 이 stale화가 더 빈번할 수 있으니 매 브리프 작성 시점마다 최신본을 재확인하는 습관이 특히 중요하다.**

**"시안 3개를 완성한 뒤 서로 직접 비교하는 단계"는 레퍼런스 대조만으로 대체되지 않는다(68차 신규 확립, 69차 2차 라운드에도 적용)**: 레이아웃 축(구조 자체가 다른지)과 팔레트 축(hex 실측 비교) 둘 다 확인해야 한다. **70차에서도 ui-designer가 3개 시안 완성 후 카드 처리 원리(보더/그림자 방식)가 A/B/C 모두 실질적으로 다름을 자체 확인 후 보고.**

**content-designer의 AI 이미지 콘텐츠(Mode A) 시안 라운드는 design-pl 없이 메인 세션이 직접 진행하면 게이트가 새어나갈 수 있다(68차 신규 확립)**.
