## 2026-08-22 (79차) — 사용자 명시 요청: `docs/harness/karpathy_skills.md` "바이브 코딩 실천 규칙"에 "판단이 필요 없는 다단계 기계적 작업은 fork로 돌린다" 불릿 신설 정합성 감사 — 가벼운 감사 (A 범위)

### 신규 발견
1. **[MEDIUM, 가능성 있음]** 신규 불릿이 "커밋→push→동기화→감사"를 판단 불필요한 기계적 체인의 예시로 들며 fork가 "스스로 끝까지 진행되고 완료되면 알림이 온다"고 서술하는데, `CLAUDE.md`("원격 저장소로의 실제 push는 매번 사용자의 명시적 확인을 받은 뒤에만 수행")·`git-workflow.md` 5절 4번("사용자에게 diff를 보여준 뒤 명시적 승인")은 push 앞에 매번 확인 게이트를 못박아둔다. fork 런칭 "전에" 확인을 받아두는 것인지, 체인 안의 push까지 fork가 알아서 넘어가는 것인지 불릿이 명시하지 않아 확인 게이트를 건너뛰는 것으로 오독될 소지. 확인 필요.
2. **[MEDIUM]** `harness-versioning.md`가 이미 "포크(fork)"를 "하네스를 다른 프로젝트로 복사해 가는 것"이라는 뜻으로 정착시켜 쓰고 있는데(포크 로그, "A에서 포크한 하네스를 B에서..."), 신규 불릿의 "fork"는 Claude Code 백그라운드 비동기 실행 기능이라는 전혀 다른 개념. 같은 하네스 문서군에서 같은 단어가 두 무관한 개념을 가리켜 문맥 없이는 헷갈릴 수 있음. 확인 필요.
3. **[LOW, 가능성 있음]** `git-workflow.md` 0절("dev-team의 어떤 서브에이전트도 git commit/push를 직접 실행하지 않는다")은 서브에이전트로 범위를 한정해 fork(메인 세션 자신의 비동기 분신)는 문언상 금지 대상이 아닌 것으로 보이나, 신규 불릿이 이 관계를 스스로 밝히지 않아 "fork가 dev-team 서브에이전트 같은 별도 주체인가"로 헷갈릴 여지. 확인 필요(경미).
4. **[LOW, 스타일]** 같은 목록의 "막히면 즉시 질문한다" 불릿은 "(1️⃣ Think Before Coding과 연결)"을 명시하는데, 신규 불릿은 4대 원칙 어디와도 연결을 밝히지 않고 층위도 달라(실행 방식 vs 코드 품질/범위/검증) 목록 내에서 다소 붕 떠 보임. 모순 아님, 참고용.

### 확인됨(문제 없음)
- 1-1절 "worktree 커밋 + 동기화는 한 세트, 같은 턴 안에" 절차와 신규 불릿 간 직접적 텍스트 모순은 없음(신규 불릿도 "판단 필요 단계는 foreground" 단서를 둠 — 다만 경계가 불명확할 뿐).
- 6절 "감사 발견은 보고 후 확인받는다" 절차와도 직접 충돌 없음.

### 패턴 메모(누적, 갱신)
- **신규 패턴(79차): 하네스 문서군에서 이미 정착된 용어(예: "포크" = 하네스를 다른 프로젝트로 복사)를 다른 문서가 완전히 다른 의미로 재사용하면, 각 문서 자체엔 내적 모순이 없어도 문서군 전체를 놓고 보면 용어 충돌이 생긴다 — 새 개념에 이름을 붙일 때 기존 하네스 전역에서 그 단어가 이미 쓰이고 있는지 먼저 확인해야 한다.**
