# 아키텍처/TRD 작성 가이드 — API 계약과 스택 선택 기준

이 문서는 기획팀 `tech-architect`가 TRD·구현요구사항서에 들어갈 기술적 판단을 만들 때 참조하는 기준이다. **특정 프레임워크/언어/인프라 선택 자체는 다루지 않는다** — 실제 스택 선택은 프로젝트마다 다른 `docs/planning/tech-architecture.md`(프로젝트별 산출물)에 남는다. 이 문서는 "어떤 기준으로 아키텍처를 판단해야 하는가"만 다룬다.

## API 계약 우선

엔드포인트, 요청/응답 스키마, 상태 코드/에러 응답 규칙이 화면정의서·기능정의서와 항상 일치하는지 확인한다. 에러 응답은 선택한 스택의 관례에 맞는 단일 형식으로 통일한다 — 문서마다 API 스펙이 따로 노는 걸 막는 게 이 역할의 핵심 가치다.

## DB 스키마 근거

테이블/관계를 정할 때 정규화 수준, 제약조건(unique, FK, cascade 등)을 왜 그렇게 나눴는지 근거를 댄다. 근거 없이 "보통 이렇게 하니까"로 정하지 않는다.

## 스택 선택은 프로젝트 범위에 맞춘다

프로젝트 성격(학습용 과제, 상용 서비스, 프로토타입 등)에 맞는 선택을 우선한다 — 실무 최적해가 정답이 아니라 "이 프로젝트가 실제로 감당 가능하면서 실무 감각도 잃지 않는" 선택. 프로젝트 범위를 넘는 인프라는 지양하고 왜 지양하는지 명시한다.

## 비기능 요구사항(NFR) 현실화

성능·보안·확장성 요구사항이 있으면 프로젝트 범위에 맞는 현실적 수준으로 정의하고, 실무 기준과 다르게 단순화한 부분은 트레이드오프로 명시한다(스코프 트레이드오프를 다루는 [[prd-writing-guide]]의 원리를 기술 쪽에 적용).

## 개발팀 CLAUDE.md 관례 인지

이 문서(TRD/tech-architecture.md 등)가 정본이고, 개발팀 각 폴더의 CLAUDE.md는 정본을 요약 참조하는 작업 가이드일 뿐이다. 파일 구조를 정의/변경할 때는 그 구조가 실제로 어느 폴더에 어떤 성격의 코드가 위치하는지(런타임 코드 폴더 vs 하네스 가이드 전용 폴더 등) 명확히 적어 개발팀이 헷갈리지 않게 한다. 정본 내용을 각 폴더 CLAUDE.md에 그대로 복사하라고 지시하지 않는다 — 개발팀이 알아서 요약해 참조하는 방식이다.

## 인용 버전 self-check

이 문서가 다른 번호/버전이 있는 문서를 인용할 때, 그 인용 버전이 stale해지지 않았는지 갱신할 때마다 확인한다. `grep`으로 자신이 인용 중인 문서명 패턴을 전부 뽑아 실제 최신 버전과 대조한다.
