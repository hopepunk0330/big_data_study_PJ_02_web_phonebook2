# 화면정의서 작성 가이드 — 4종 세트와 오버레이

이 문서는 `planning-writer`가 화면정의서를 쓸 때 지키는 구조 패턴이다. **특정 화면이 실제로 어떻게 생겼는지(레이아웃, 컴포넌트 값)는 다루지 않는다** — 그건 프로젝트별 디자인 산출물(`docs/design/confirmed/`)의 몫이다. 이 문서는 "화면 하나를 정의할 때 빠짐없이 갖춰야 하는 구조"만 다룬다.

## 4종 세트는 예외 없이 필수

화면마다 아래 4가지가 모두 있어야 한다.

1. 목적(한 줄)
2. ASCII 와이어프레임
3. 구성요소-동작 표(요소 / 사용자 동작 / 호출 API / 성공 시 / 실패 시)
4. Mermaid flowchart(상태 분기 — 성공/실패/조건/다른 화면 이동)

문서 안에 화면(SCR-*)이나 화면 전환이 언급되면 반드시 시각적으로(와이어프레임 또는 전환 다이어그램) 그려져야 한다 — 서술 문장 한 줄로 때우고 넘어가지 않는다. 버전을 마무리하기 전 문서 안의 화면 헤딩을 전부 훑어 각각에 4종 세트가 실제로 다 있는지 자체 점검한다 — 한 화면이라도 빠졌으면 그 라운드를 완료로 보고하지 않는다.

## "화면"의 범위 — 오버레이 포함

전체 페이지 화면만이 아니라 팝업/모달/얼럿/토스트/배너/바텀시트처럼 다른 화면 위에 잠깐 뜨는 오버레이도 전부 화면정의서의 대상이다 — 스토리보드라면 그려질 모든 프레임이 대상이다. 확정 디자인에 이미 그 오버레이 프레임이 있으면 그 실제 레이아웃을 근거로 와이어프레임을 그린다 — 구성요소 표에 "모달 오픈"처럼 동작 한 줄만 적고 그 모달이 실제로 어떻게 생겼는지는 그리지 않고 넘어가지 않는다. 횡단 관심사 화면(공통 메시지/오류 표시 등)도 예외가 아니다 — 4종 세트를 똑같이 갖춘다.

## 바텀시트 지시는 "컨테이너만 교체하라"가 아니라 "스텝을 나누라"는 신호다(2026-08-24 신설)

기획·리뷰 단계에서 "이건 바텀시트로 해줘"라는 지시가 나오면, 전체 화면에 있던 내용을 그대로 축소해 바텀시트 컨테이너 안에 욱여넣는 것으로 처리하지 않는다. 그 지시의 진짜 의도는 대부분 "한 번에 다 보여주지 말고, 지금 당장 필요한 만큼만 먼저 보여준 뒤 다음 단계로 진행시키는 흐름으로 다시 쪼개라"는 것이다 — 바텀시트라는 형태(컴포넌트)가 목적이 아니라, 그 형태가 자연스럽게 강제하는 점진적 공개(한 화면=한 결정/한 입력 단위)가 목적이다. 전체 화면 내용을 그대로 옮기기만 하면 담는 그릇만 바뀌었을 뿐 정보 밀도·스크롤량·한 번에 봐야 하는 선택지 수는 그대로라 사용성이 개선되지 않는다.

- **적용 방법**: 원래 화면에 있던 필드/선택지/섹션을 목록으로 나열한 뒤, "사용자가 이 시점에 결정을 내리는 데 지금 당장 필요한 것"과 "다음 결정으로 넘어가야 볼 수 있는 것"으로 나눈다. 나뉜 묶음 하나하나가 바텀시트의 한 스텝(또는 한 단계 확장)이 된다 — 스텝이 하나뿐이면 애초에 바텀시트로 굳이 나눌 이유가 없다는 뜻이므로, 오히려 원래 지시를 다시 확인한다.
- **화면정의서 반영**: 스텝이 여러 개면 그 각각을 별도 화면(SCR-xxx-1, SCR-xxx-2 등)이나 같은 화면의 상태 분기로 취급해 4종 세트(위 "4종 세트" 절)를 갖추고, 스텝 간 이동은 그 화면의 Mermaid flowchart에 상태 분기로 그린다 — "바텀시트 열림"이라는 동작 한 줄로 뭉뚱그리지 않는다.
- **판단이 애매하면 질문한다**: 원문 지시가 정말 "레이아웃만 바텀시트 모양으로 바꿔달라"는 뜻일 수도 있다(드물지만 존재) — 스텝 분해가 맞는지 자체 판단만으로 밀어붙이지 않고, 원래 화면의 선택지·필드 수가 많아 명백히 한 번에 보여주기 부적절한 경우가 아니라면 어느 쪽 의도인지 확인한다.

## 동적 목록 명시

와이어프레임·구성요소 표에 데이터 개수에 따라 늘어나거나 줄어드는 목록이 나오면, 그 목록이 최소~최대 범위에서 유연하게 렌더링된다는 것을 명시한다. 와이어프레임엔 그 시점의 예시 개수만 그려지지만, 실제로는 고정 개수가 아니라는 안내를 목록형 요소마다 붙인다.

## 집계값의 출처 명시

카운트·집계 표시(예: "항목(N)")가 있으면 그 값이 어디서 오는지(전용 API 필드인지, 이미 로드된 목록에서 클라이언트가 집계한 파생값인지)도 함께 명시한다 — API 계약에 없는데 문서에만 나오는 숫자는 나중에 프론트엔드 개발자가 그 값을 어디서 가져오나 헷갈리게 만든다.

## 디자인 언어가 의도적으로 분리된 화면은 그 경계를 화면정의서 본문에 못박는다(2026-08-22 신설)

백오피스/통계 대시보드처럼 프론트(고객용) 화면과 완성도·스타일을 의도적으로 다르게 가져가는 화면(→ `docs/harness/design-team/figma-file-organization.md` 3-D번)이 있으면, 그 사실을 하네스 문서에만 남기지 않고 **그 화면의 화면정의서 항목 본문에도 명시적으로 적는다** — 예: "SCR-xxx의 스타일은 프론트(고객용) 화면과 무관한 별도 디자인 언어이며, 이후 UI/UX 디자인 작업 시 이 스타일을 참고·재사용하지 않는다." 하네스는 일반 원칙만 담고 있어 나중에 이 문서만 보는 사람(다른 디자이너, 다음 라운드의 워커)이 하네스까지 거슬러 올라가지 않을 수 있다 — 그 화면을 다루는 바로 그 자리에 경계를 남겨야 실수로 스타일이 역류하는 걸 막을 수 있다.

## 문서 전체 구성 순서

위 4종 세트는 화면 "하나"의 구조다. 문서 전체는 그 화면들을 담는 그릇이라 별도로 순서가 필요하다 — 화면별 상세부터 바로 나열하지 않는다.

1. **화면 목록 표(개요)**: 화면 ID(SCR-xxx) / 화면명 / 보이는 조건(언제 나타나는가) / 대응 요구사항(FR-xx). 화면별 상세로 들어가기 전에 전체 화면이 몇 개고 서로 어떻게 다른지 한눈에 보여준다.
2. **화면별 상세**(위 4종 세트, 화면 목록 순서 그대로).
3. **화면 전이도**: 화면 목록에 없던 "화면 간 이동 규칙"을 별도로 다룬다 — 각 화면 상세의 flowchart가 "그 화면 안에서의 상태 분기"라면, 이건 "어느 화면에서 어느 화면으로 넘어가는가"를 다루는 문서 전체 단위의 다이어그램이라 화면별 flowchart와 중복이 아니다.
4. **공통 규칙 섹션**: 오류 표시, 이중 제출 방지처럼 특정 화면 하나에 속하지 않고 문서 전체에 적용되는 규칙은 화면 하나로 취급해 4종 세트를 갖추거나(예: 공통 메시지 영역을 그 자체로 화면처럼 정의) 별도 섹션으로 모아 마지막에 둔다 — 화면마다 반복 서술하지 않는다.
