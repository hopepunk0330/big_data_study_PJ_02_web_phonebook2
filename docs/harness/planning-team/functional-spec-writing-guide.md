# 기능정의서 작성 가이드 — 입력/처리/출력/예외 스펙

이 문서는 기획팀이 기능정의서(기능 단위 상세 스펙)를 쓸 때 참조하는 구조 기준이다. PRD가 "왜/무엇을"을 다룬다면 기능정의서는 "정확히 어떻게 동작하는가"를 다룬다. 화면 자체의 레이아웃·구성요소는 [[screen-spec-pattern-guide]]의 몫이고, 이 문서는 그 화면 뒤에서 일어나는 기능 로직의 스펙만 다룬다.

## 기능 단위 스펙 구조

기능 하나마다 아래 항목을 빠짐없이 정의한다.

- **기능 ID(FR-xx)** — PRD/화면정의서와 매핑 가능해야 한다(추적성. [[test-plan-design-guide]]에서 qa-planner가 이 ID로 테스트 케이스를 연결한다).
- **트리거/사전조건** — 이 기능이 언제, 어떤 상태에서 실행되는가.
- **입력** — 어떤 값이 어떤 형식·제약으로 들어오는가.
- **처리 절차** — 단계별로 무엇을 하는가(순서가 중요하면 번호로 명시).
- **출력** — 성공 시 무엇을 반환·표시하는가.
- **예외 케이스** — 실패·경계 상황마다 어떻게 처리하는가(입력 검증 실패, 권한 없음, 대상 리소스 없음 등).

## 복잡한 분기는 flowchart로 보완

로직 분기가 여러 조건으로 얽히거나, 여러 단계를 거쳐 최종 결과가 갈리는 기능은 서술만으로 끝내지 않고 Mermaid flowchart로 보완한다. 조건이 하나뿐인 단순 기능까지 억지로 다이어그램화하지 않는다 — 분기가 복잡할 때만 적용한다.

## ID 추측 금지

새 FR 번호를 매기는 원칙은 [[document-versioning-guide]]의 "ID 번호는 추측하지 않고 실제로 확인" 규칙을 그대로 따른다 — 관련 문서(PRD, 화면정의서 등)를 실제로 열어 번호가 비어 있는지 확인하고, "아마 다음 번호겠지"로 임의 배정하지 않는다.

## 화면/API와의 연결 명시

이 기능이 어느 화면(SCR-xx)에서 트리거되고 어떤 API 계약(tech-architect가 정한)을 호출하는지 상호 참조를 남긴다 — 기능정의서만 봐서는 화면·API와 어떻게 연결되는지 알 수 없는 상태로 두지 않는다.
