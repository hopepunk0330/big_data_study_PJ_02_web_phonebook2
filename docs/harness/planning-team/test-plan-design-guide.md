# 테스트 계획 설계 가이드 — 동등분할·추적성·위험기반 우선순위

이 문서는 `qa-planner`가 테스트 케이스를 설계할 때 참조하는 기준이다. **실제 테스트 코드 작성·실행은 다루지 않는다** — 이건 코드가 존재해야 의미 있는 작업이라 개발팀(qa-engineer)의 몫이다. 이 문서는 "테스트 케이스를 어떻게 도출하고 어떤 기준으로 우선순위를 매길지"만 다룬다.

## 동등분할 + 경계값 분석

입력 하나마다 모든 값을 다 테스트하지 않는다. 유효/무효 동등 클래스로 나누고, 그 경계(최소/최대/바로 위·아래)만 대표로 뽑는다.

## 추적성(Traceability)

모든 테스트 케이스는 근거 ID(AC-xx, FR-xx, SCR-xxx — [[functional-spec-writing-guide]]·[[prd-writing-guide]] 참고)에 매핑돼야 한다 — 근거 없는 케이스를 만들지 않고, 반대로 근거 중 테스트 케이스가 하나도 없는 게 있으면 커버리지 갭으로 지적한다.

## 화면정의서 flowchart를 1차 소스로 사용

화면정의서([[screen-spec-pattern-guide]])에 이미 각 화면의 성공/실패/조건 분기가 노드·화살표로 정리돼 있다면, 처음부터 다시 궁리하지 않고 그 다이어그램을 계통적으로 순회하며 케이스를 뽑는다 — 이 분기 하나하나가 잠재적 테스트 케이스다.

## 단위 vs 통합 테스트 구분

단위 테스트는 함수 하나를 격리해서(의존성 mock) 검증하고, 통합 테스트는 실제 API 요청 → DB 반영 → 응답까지 전체 흐름을 검증한다. 같은 기능이라도 두 레벨에서 각각 무엇을 검증하는지 다르게 설계한다.

## 위험 기반 우선순위

인증/권한처럼 보안이 걸린 경로는 두껍게(정상/실패/경계/악의적 입력까지), 단순 CRUD는 필요한 만큼만 설계한다 — 모든 조합을 기계적으로 다 만들지 않는다.

## 테스트 독립성

각 테스트 케이스가 다른 테스트의 실행 순서나 상태에 의존하지 않고 단독으로 재현 가능하게 설계한다.

## 원본 문서 오류는 임의로 처리하지 않는다

화면정의서/PRD/아키텍처 문서의 내용이 서로 모순되면(예: 상태 코드가 문서마다 다르게 적혀 있으면) 테스트 케이스를 임의로 한쪽 기준에 맞춰 만들지 않고 보고해 확인받는다.

## 체크리스트

- [ ] 각 입력마다 동등분할+경계값이 대표로 뽑혔는가?
- [ ] 모든 케이스가 AC/FR/SCR 중 하나에 매핑되는가? 반대로 커버리지 갭이 있는가?
- [ ] 화면정의서 flowchart의 분기가 전부 케이스로 순회됐는가?
- [ ] 단위/통합 레벨이 명확히 구분됐는가?
- [ ] 보안/인증 경로가 위험기반으로 두껍게 설계됐는가?
- [ ] 각 케이스가 다른 케이스 상태에 의존하지 않는가?
