# 안드레 카파시(Andrej Karpathy) 행동지침

## 4대 원칙

### 1️⃣ Think Before Coding

첫 번째는 코딩하기 전에 생각하라는 규칙이다.

요구사항이 애매한데도, Claude가 스스로 해석해서 바로 구현을 시작하는 경우가 있다.

이를 막기 위한 장치라고 생각하면 된다.

- 가정을 명시하기
- 불확실하면 질문하기
- 여러 해석이 가능하면 선택지를 제시하기

해당 부분은 Karpathy가 말한 “AI는 혼란을 관리하지 못하고, 질문하지 않는다”는 문제를 담고있는 것 같다.

### 2️⃣ Simplicity First

두 번째는 단순함을 우선하라는 규칙이다.

간단한 기능 하나를 요청했는데, 불필요한 확장·추상 클래스를 함께 만들어버리는 경우가 있다.

해당 규칙은 과잉 구현을 명확히 금지한다.

- 요청받지 않은 기능 추가 금지
- 한 번만 쓰는 코드에 추상화 금지
- 요구하지 않은 유연성·설정화 금지
- 불가능한 시나리오에 대한 과한 예외 처리 금지
- 200줄로 작성했는데 50줄로 가능하다면 다시 단순화

개인적으로 가장 마음에 들었던 문장은 아래 기준이다.

> Would a senior engineer say this is overcomplicated?

즉, AI에게 “시니어 개발자가 봤을 때 과한 설계인가?”를 스스로 점검하게 만드는 것이다.

### 3️⃣ Surgical Changes

세 번째는 수술하듯 필요한 부분만 수정하라는 규칙이다.

AI Agent에게 기존 코드를 맡겼을 때 가장 무서운 부분은 작업 범위가 너무 광범위해진다는 것이였다.

해당 규칙은 이를 명확하게 금지하고 있다.

- 꼭 필요한 파일과 라인만 수정하기
- 주변 코드, 주석, 포맷팅을 임의로 개선하지 않기
- 깨지지 않은 코드를 리팩토링하지 않기
- 기존 스타일이 마음에 들지 않아도 맞춰가기
- 관련 없는 dead code는 삭제하지 말고 언급만 하기

여기서 핵심 기준은 매우 명확하다.

> Every changed line should trace directly to the users request.

즉, 변경된 모든 라인은 사용자의 요청과 직접 연결되어야 한다는 의미다.

### 4️⃣ Goal-Driven Execution

네 번째는 목표 기반으로 실행하라는 규칙이다.

이 부분이 Karpathy의 생각과 가장 직접적으로 연결된다고 느꼈다.

Karpathy는 AI에게 세부 구현을 지시하기보다, 성공 기준을 주고 반복하게 하라고 말했다.

forrestchang의 Skill도 동일하게 작업을 검증 가능한 목표로 바꾸도록 유도한다.

- validation 추가 → "잘못된 입력에 대한 테스트를 작성하고 통과시키기"
- 버그 수정 → "버그를 재현하는 테스트를 작성하고 통과시키기"
- 리팩토링 → "수정 전후 테스트가 모두 통과하는지 확인하기"

멀티 스텝 작업에서는 아래처럼 각 단계마다 검증 기준을 두는 방식이다.

1. 요구사항 분석 → verify: 불확실한 부분 질문
2. 최소 변경 구현 → verify: 변경 범위 확인
3. 테스트 실행 → verify: 기존 테스트 통과

## 바이브 코딩 실천 규칙

4대 원칙을 이 프로젝트의 "바이브 코딩" 협업 방식에 맞게 구체화한 실천 규칙이다.

- **의도는 자연어로, 검증은 코드로**: 요구사항은 자연어로 편하게 전달해도 되지만, 결과물은 반드시 실행하거나 테스트로 검증한다.
- **AI를 주니어 개발자로 취급한다**: AI가 만든 결과를 무조건 신뢰하지 않고 사람이 최종 확인·승인하며, 의심스러운 결과는 재작업을 요청한다.
- **작은 단위로 반복한다**: 한 번에 큰 기능을 통째로 요청하지 않고 작은 단위로 나누어 요청하고 매 단계마다 결과를 확인한다.
- **막히면 즉시 질문한다**: 요구사항이 모호하면 AI가 임의로 해석해서 진행하지 않고 먼저 질문하거나 선택지를 제시한다. (1️⃣ Think Before Coding과 연결)
- **판단이 필요 없는 다단계 기계적 작업은 에이전트 fork(Agent 도구의 fork 서브타입)로 돌린다(2026-08-22 신설)**: 여기서 말하는 "fork"는 `harness-versioning.md`의 "하네스 포크"(하네스를 다른 프로젝트로 복제·이식하는 것)와는 다른 개념이다 — 이건 지금 세션 안에서 백그라운드 작업을 병렬로 띄우는 Agent 도구 기능을 가리킨다. 커밋→동기화→감사처럼 이미 방향이 정해진 뒤의 반복 체인 작업은 foreground(메인 세션이 직접 붙잡고 순서대로 실행)로 하지 않고 이 fork로 돌린다 — foreground로 하면 그 중간에 사용자가 다른 질문을 던졌을 때 답하고 나서 원래 하던 작업으로 돌아가는 걸 깜빡할 위험이 있다. fork는 대화 스레드와 독립적으로 백그라운드에서 계속 실행되므로, 질문에 답하는 것과 무관하게 스스로 끝까지 진행되고 완료되면 알림이 온다 — 작업이 중간에 끊겨 잊히는 걸 막는 구조적 안전장치다. 반대로 그 자리에서 사용자와 주고받으며 판단해야 하는 작업(무엇을 할지 확정하는 단계, 여러 방향 중 고르는 단계)은 계속 foreground에서 한다. 이 fork도 결국 메인 세션 자신의 연장이라(dev-team 서브에이전트가 아님) `git-workflow.md` 0절("git 실행 권한은 메인 세션에만")과 모순되지 않는다 — 다만 **"금지" 항목(원격 저장소 push는 매번 명시적 확인 후)에 해당하는 push는 이 기계적 체인에 무조건 포함시키지 않는다**: 현재 `CLAUDE.md` "금지" 절이 명시적으로 예외를 둔 채널은 `harness` 브랜치 → `origin` push, 이 하나뿐이다 — 이 채널로의 push만 fork 체인에 포함하고, 그 외 모든 push(`assignment`, `main`→`assignment`/`origin` 등)는 매번 새로 확인이 필요하므로 fork 안에 자동으로 넣지 않고 결과를 보고한 뒤 별도로 확인받는다. 새로운 채널이 "반복적으로 승인됐다"고 판단해 이 예외 목록에 스스로 추가하지 않는다 — 예외를 늘리는 건 `CLAUDE.md` 자체를 고치는 별도 결정이다.

- **백그라운드 라운드가 API 오류(사용량 한도 등)로 중간에 끊기면, 재개 전에 반드시 실제 상태부터 재검증한다(2026-08-26 신설)** — 로직 실패("이 조건에서 이렇게 처리하면 안 된다")가 아니라 "You've hit your session limit" 같은 API 레벨 강제 종료는 어디까지 실제로 완료됐는지 불확실하게 만든다(부분 완료된 파일·컴포넌트가 남아있을 수 있고, 대상 노드/파일이 그 사이 다른 경로로 바뀌어 있을 수도 있다). 재개 지시를 내리기 전에: ① 그 사이 생긴 로컬 변경사항(agent-memory, docs/design 등)을 먼저 커밋해 유실을 막는다, ② 재개하는 워커에게 "처음부터 다시 하지 말고 `get_metadata`/`git status`로 현재 상태부터 재확인한 뒤 이어가라"고 명시적으로 지시한다 — 이전 라운드가 남긴 산출물(예: graphic-designer의 정리 결과 문서)을 먼저 읽고 그대로 이어받게 한다. **배경 작업이 멈춘 것처럼 보이거나 이상한 도구 배정 오류가 보고되면(예: "서브에이전트에 Agent 도구가 배정되지 않음"), 지레짐작으로 판단하지 않고 `ListAgents`로 실제 하위 에이전트 생존 여부를 확인하고 Figma/파일시스템의 실제 상태를 직접 조회해서 판단한다** — 이런 도구 배정 버그 자체는 Claude Code 런타임 이슈라 하네스 규칙으로 고칠 수 없지만, 그로 인해 작업이 실제로 멈췄는지 아니면 계속 진행 중인지는 항상 직접 확인 가능하다.
