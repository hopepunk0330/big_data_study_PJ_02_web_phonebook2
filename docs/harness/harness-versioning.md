# 하네스 버전 판별 — 여러 프로젝트 사본 중 최신 찾기

## 배경

이 하네스(`.claude/agents/**`, `docs/harness/**` 등)는 git submodule이 아니라 단순 파일 복사(`cp -r`)로 여러 프로젝트에 옮겨 쓴다. 그러다 보니 A 프로젝트에서 포크한 하네스를 B에서 더 발전시키고, B에서 다시 C로 포크하는 식으로 여러 갈래로 나뉠 수 있다. 이 문서는 그 상태에서 "지금 디스크에 존재하는 여러 사본 중 어느 게 최신인지" 판별하는 절차를 정리한다.

`claude-harness.md`(파일이 무엇을 통제하는가), `git-workflow.md`(한 프로젝트 안의 브랜치 전략), `reset-checklist.md`(한 프로젝트를 리셋할 때 A/B/C 분류)와는 각도가 다르다 — 이 문서만 "프로젝트 여러 개에 흩어진 하네스 사본들 사이의" 비교를 다룬다.

CLAUDE.md의 `origin`(JY_Harness) 리모트 관례처럼 중앙 허브 저장소로 계속 동기화하는 프로젝트도 있지만, 로컬 사본이 허브로 다시 push되기 전까지는 여러 갈래가 동시에 존재할 수 있다. 이 문서의 절차는 허브 동기화 여부와 무관하게, 지금 손에 있는 사본들만 놓고 최신을 가리는 방법이다.

## 1순위 기준 — git 커밋 날짜 비교

하네스를 고칠 때마다 그 변경을 담은 프로젝트 저장소에 커밋해 남긴다. 여러 프로젝트 중 최신을 고를 땐, 후보가 되는 각 프로젝트 저장소에서 아래 명령으로 하네스 관련 경로의 마지막 변경 날짜를 비교한다.

```bash
git log -1 --format="%cd" -- .claude/ docs/harness/
```

가장 최근 날짜가 나온 프로젝트가 최신이므로, 거기서 복사해간다. 별도 유지보수 없이 자동으로 정확하다는 게 장점 — 이 기준이 항상 1순위다.

**주의**: 이 비교는 "가장 최근에 손댄 사본"만 알려줄 뿐 "가장 많은 개선사항을 담은 사본"을 보장하지 않는다. 뒤처진(포크 이후 원본 쪽이 더 발전한) 사본에서 실수로 하네스를 고쳐 커밋해버리면, 그 순간 커밋 날짜만 보면 그 사본이 최신처럼 보이지만 실제로는 다른 갈래의 개선사항이 반영 안 된 채로 다시 갈라진 것이다. 아래 "작업 전 예방"과 "뒤늦게 발견했을 때"를 함께 따른다.

## 작업 전 예방 — 하네스를 고치기 시작하기 전에 반드시 확인

어느 프로젝트에서든 `.claude/`, `docs/harness/`를 고치기 시작하기 **전에**:

1. 이 프로젝트의 포크 로그(아래 "포크 로그" 표)를 열어 이 사본이 어디서(From) 포크됐는지 확인한다.
2. 가능하면 그 출처 저장소에 접근해 `git log -1 --format="%cd" -- .claude/ docs/harness/`로 출처 쪽의 마지막 변경일을 확인하고, 지금 고치려는 이 사본에서 같은 명령을 돌린 결과와 비교한다.
3. 출처 쪽이 이 사본의 포크 시점 이후로 더 앞서 나갔다면(출처가 더 최신이라면), 먼저 그 최신 사본을 받아와 이 프로젝트에 반영한 뒤에 작업을 시작한다 — 뒤처진 사본 위에 그대로 새 수정을 얹지 않는다.
4. 출처 저장소에 접근할 수 없는 경우(로컬에서 지워졌거나 다른 컴퓨터에 있는 경우 등)에는 최소한 포크 로그의 "그 시점 상태 요약"만이라도 참고해, 이 사본이 명백히 뒤처진 상태(로그상 그 이후 다른 갈래에서 여러 차례 포크·개선이 있었던 게 보이는데 이 사본은 그 이전 상태)인지 확인한다.

## 뒤늦게 발견했을 때 — 수동 병합

서로 다른 git 저장소의 히스토리는 git이 자동으로 합쳐주지 못한다(공통 조상이 있어도 별도 저장소면 merge/rebase로 자동 통합되지 않는다). 이미 실수로 갈라진 걸 뒤늦게 발견했으면:

1. 갈라진 두 사본의 `.claude/`, `docs/harness/`를 나란히 놓고 사람이 직접 diff한다(예: `diff -rq harness-A/.claude harness-B/.claude`, 또는 파일별 `diff`).
2. 자동 병합을 시도하지 않고, 차이를 하나씩 검토해 수동으로 병합한다 — 어느 쪽이 의도된 개선이고 어느 쪽이 뒤처진 사본에서 나온 중복/충돌 수정인지는 기계적으로 판단할 수 없다.
3. 병합이 끝나면 병합된 쪽 저장소에 커밋하고, 이 사건 자체를 포크 로그에 한 줄 남긴다(예: "날짜 — 두 갈래(X, Y) 수동 병합 — 원인: 뒤처진 사본에서 수정 후 커밋").

## 2순위(보조) 기준 — 포크 로그

여러 저장소를 일일이 열어 `git log`를 돌려보지 않고, 아래 로그 한 곳만 훑어서 전체 계보를 파악하기 위한 요약이다.

- 하네스를 고칠 때마다 적지 않는다 — 그건 이미 git 커밋 기록이 원본이다(1순위 기준이 그걸 본다).
- **새 프로젝트로 하네스를 포크해갈 때만** 아래 표에 한 줄 추가한다: 날짜 — 어디서 어디로 포크했는지 — 그 시점 상태 한 줄 요약.
- 이 로그와 git 커밋 기록이 어긋나면(예: 로그에 없는 포크가 있었거나 날짜가 틀렸거나) **git 커밋 기록을 우선**한다. 이 로그는 훑어보기용 보조 자료일 뿐, 진실의 원천이 아니다.

이 표의 각 행은 "예시 문구"가 아니라 실제로 있었던 포크 이력이다 — `reset-checklist.md` C-3(예시에 박힌 프로젝트명·노드 ID를 리셋 시 치환 검토하는 항목)의 대상이 아니며, 새 프로젝트로 하네스를 복사해갈 때도 지우지 않고 그대로 들고 가서 이어서 기록한다.
